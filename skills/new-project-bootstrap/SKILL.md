# 新项目初始化

把新项目从需求梳理推进到可运行的初始版本，并补齐仓库指引、设计规范和结构图。先借助 Google AI Studio 生成高质量 Web 界面原型，再由开发代理在最终目标平台实现产品功能。首个产品版本保持最小、可运行。

## 流程

1. **检查项目并理解需求。** 查看当前目录、现有文件和 `AGENTS.md`，保留已有内容。将新项目视为架构型任务，使用 `superpowers:brainstorming` 逐个询问项目目的、目标用户、首版必需能力、平台、限制和成功标准。明确询问用户希望的设计风格，以及是否有参考网站、产品或截图；如果用户尚未确定，可根据项目定位给出 2–3 个风格方向供选择。每次只问一个重点问题，不擅自扩展需求。分别记录最终产品的功能规格与 AI Studio 阶段的界面设计范围。

   如果当前环境没有 brainstorming skill，从 [obra/superpowers](https://github.com/obra/superpowers) 获取完整技能套件，并安装到当前项目的 `.agents/skills/`。先把官方仓库取到临时目录，再将 `skills/` 下每个完整 skill 目录复制到项目中；保留配套文件和已有 skill，遇到同名冲突时不要覆盖。安装好后继续 brainstorming。

2. **生成 Gemini 界面设计提示词。** 需求明确后，生成一份可直接复制到 [Google AI Studio](https://aistudio.google.com/) 的中文提示词。使用 AI Studio 的目的是获取高质量视觉设计，**提示词始终要求生成 Web 应用，只负责界面设计和必要的交互演示，不要求实现实际业务功能**。最终产品无论是 Web、Android、iOS 或桌面应用，都按这一范围要求 AI Studio；最终产品平台用于说明设计背景、目标设备和交互习惯，不改变本阶段交付的 Web 形式。

   提示词依次写清：产品背景与主要用户；用户选定的设计风格及参考；必要页面、布局与组件；空状态、加载、成功和错误等视觉状态；仅用于演示的交互；完整 Web 源码、资源和预览方式。业务流程、数据和持久化需求只作为界面设计背景，不要求 Gemini 实现后端、API、真实存储、设备能力或业务引擎。允许本地组件状态、模拟数据和模拟进度来演示界面，明确它们不是真实业务结果，也不是最终产品新增功能。

   要求 Gemini 将精力用于排版、颜色、间距、布局、组件细节和状态设计，生成最小可预览的 Web 界面原型；不添加未要求的功能、无关 SDK、服务、Gemini API 或复杂架构。非 Web 最终产品不要求它生成原生工程、安装包、平台构建配置或真实功能。可将原型放入 `design-reference/web/` 等独立目录，避免混淆视觉参考与正式应用。

   展示提示词，并请用户亲自到 AI Studio 生成 Web 界面原型，将完整源码及相关资源放入项目。**在此暂停。** 只有用户确认文件已放入项目或提供了文件路径后才能继续。在等待期间不要自行搭建、安装依赖或改写项目文件。

3. **审查并中性化 Web 界面原型。** 完整检查用户放入的目录、界面源码、样式、资源、依赖、脚本、预览配置和文档，对照已确认的设计风格、页面与交互状态范围。此时审查的是视觉原型，模拟数据和模拟交互是预期产物；不因原型没有后端或真实业务功能就判定它不合格，也不将模拟成功当作最终产品功能已完成。

   找出 AI Studio/Gemini 平台专用的包装层、运行时假设、部署适配、无关 SDK、示例代码和配置。删除与界面设计无关的平台代码；需要保留的界面与演示交互改用标准 Web 预览实现，清理对应依赖、导入、脚本、环境变量示例和文档引用。保留呈现已选设计所需的样式、资源和演示状态。若最终产品明确需要 Gemini API，将其列为后续真实功能实现项，不让界面原型承担这项集成。清理后确认视觉设计可预览，再进入架构判断。

4. **判断最终产品架构。** 以已确认的最终产品平台和功能规格为依据，识别实际需要的应用、可独立部署的服务和共享包。**Web 视觉原型的技术栈不决定最终产品的技术栈**；非 Web 产品需提取设计并在目标平台实现界面和功能，不能把 Web 原型包装成用户未要求的替代产品。

   只要技术上可行且架构适用，就采用基于 pnpm workspace 的 monorepo；workspace 边界只覆盖真实存在的应用和包。Web 设计参考本身不构成增加正式应用、服务或 monorepo 的理由。如果有明确技术限制导致 monorepo 不适用，说明限制并推荐最简单兼容的架构，取得用户同意后再按该架构继续。已有明确架构授权时按已确认方案执行。

5. **补充项目指引。** 将以下原则追加到根目录 `AGENTS.md`；文件不存在时创建。保留原有指引，并避免重复添加：

   - 选择能够完全满足当前需求的最简单实现。避免预防性的抽象、额外配置和不必要的间接层。
   - 逐层构建系统。从能够端到端运行的最小版本开始，在已经可以正常工作的产品之上逐步增加新的能力。不要为了尚未完成的复杂设计，牺牲一个已经能够正常工作的产品。
   - 保持组件模块化，并明确分离不同关注点。
   - 如果成熟且维护良好的现有库能够降低整体复杂度或提高可靠性，优先使用它。没有明确理由，不要重新实现已有的通用功能。
   - 在自己实现功能或添加新的依赖包之前，优先利用项目中已经存在的依赖。不要在没有检查文档和类型定义之前，就假设某个库不具备所需能力。
   - 架构决策要面向长期。不要接受“先这样做，以后再替换”的临时方案。

6. **总结设计规范。** 根据清理后的 Web 原型 UI 源码、样式、资源文件和用户提供的截图，按照 [Google Labs DESIGN.md 格式](https://github.com/google-labs-code/design.md) 在项目根目录生成 `DESIGN.md`。记录有证据支持的颜色、字体、间距、布局、形状、组件状态和响应式行为。非 Web 产品同时记录这些设计在目标平台的对应方式，明确原型数据和演示控件不属于正式产品要求。不要臆造品牌决策；无法确定的数值在正文中标为估算。使用 `npx --yes @google/design.md lint DESIGN.md` 校验，不把 CLI 加入项目依赖。

7. **用 Graphify 总结项目结构。** 按照 [Graphify 官方说明](https://github.com/Graphify-Labs/graphify) 操作。若 CLI 不存在，优先用 `uv tool install graphifyy` 安装隔离环境中的命令行工具，然后为当前仓库安装：`graphify install --project --platform codex`。使用 Codex skill 执行 `$graphify .`，保留有用的项目产物，包括 `graphify-out/GRAPH_REPORT.md` 和图文件。区分视觉参考与正式应用，避免把原型的演示逻辑描述为产品业务能力。只有项目确实需要时才安装 Graphify 可选扩展。

8. **实现并审计最终产品功能。** 以已确认功能规格为验收依据，以 Web 界面原型和 `DESIGN.md` 为视觉参考。对于非 Web 产品，在目标平台建立或沿用正式工程，将原型设计转为该平台界面；对于 Web 产品，可在清理后的界面代码上接入真实功能。只处理已确认范围，不顺手添加新功能。

   审查正式工程对页面、交互、真实数据流、本地持久化、设备适配、错误处理和空状态的覆盖，记录每项是已完成、部分完成、缺失还是行为不符，并附上文件或可复现行为。原型缺少真实功能是设计阶段的预期结果，真实功能在本步骤实现；原型能预览或构建不代表最终产品已经完成。模拟进度、演示数据和状态切换控件不能作为功能验收证据，也不直接进入正式用户流程。本步骤无需修改或校验 `DESIGN.md`。

   基于实际工程和审计结果制定可执行实施计划，拆分任务并标明相关文件、依赖关系和适当的验证方式；有 `superpowers:writing-plans` 时使用该 skill，并将计划保存在项目计划目录。随后按计划逐项实现缺失或不完整的功能，不要停在审查报告或计划上。沿用确定的产品架构与现有依赖，在每项完成后做与改动相称的检查；若有重要需求无法从已确认规格推断、或必须扩大产品范围才能继续，再向用户提问。全部实现后，重新逐项核对需求覆盖情况，运行最终目标平台适用的构建和检查，并执行 `graphify update .` 同步结构图。

完成后分别汇报 Web 界面原型与最终产品的状态，以及架构选择、创建或修改的文件、功能实现与审计结果、校验结果和未完成事项。没有实际执行 AI Studio 手动步骤、Graphify、设计校验或目标平台构建时，不要声称已经完成。
